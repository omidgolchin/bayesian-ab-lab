Bayesian A/B Lab

I built this to understand how to read an A/B test two ways — the classic significance test and the Bayesian read — and to check where each one misleads: what peeking does to both, and whether a language model reads results correctly when it answers from judgement versus when it writes the code.

What happens if you keep looking?

Simulate thousands of A/B tests where A and B are identical, check the accumulating data every 250 visitors per arm, and stop at the first "positive" read. Any positive is a false alarm — so how often does each stopping rule produce one?

The honest part: the Bayesian rule is not immune. Its false-positive rate climbs with the number of looks too. Stopping when the expected loss is small changes the currency of the decision — you stop when being wrong is cheap, not when a line is crossed — but with unlimited looks and a fixed threshold it still manufactures confident wrong answers more often than the threshold suggests. (Armitage, McPherson & Rowe tabulated the classic case in 1969; the × marks are their numbers.)

The fix is boring and free: decide the sample size before you start, from a power calculation, then look once.

Adaptive allocation: Thompson sampling vs 50/50

Instead of splitting traffic evenly, Thompson sampling shifts visitors toward whichever arm currently looks better. It earns more conversions during the test. The cost shows up after it: the losing arm gets starved of data, so the final read is weaker. Both halves of the trade are in the numbers below — simulated, 2,000 tests of 4,000 visitors each.

Can an LLM read an A/B result?

Thirty fixed A/B summaries — clear wins, ties, small samples, borderline reads, and results that were peeked into existence — put to language models two ways. Direct: answer from judgement (a decision, a probability, any concerns). Code: write Python that computes the answer, which is then run and scored, not trusted. Ground truth is this page's own calculator under a decision rule fixed before the run (ship at ≥ 95% probability with expected loss ≤ 0.2 points; a peeked result can never justify shipping).

Methods & sources. The Bayesian read is the standard Beta-binomial treatment (Gelman et al., Bayesian Data Analysis, 3rd ed., 2013). The peeking analysis follows Armitage, McPherson & Rowe (1969), "Repeated significance tests on accumulating data", JRSS A 132(2):235–244, and Evan Miller's "How Not To Run an A/B Test" (2010). Cookie Cats data: "Mobile Games: A/B Testing" (Yufeng Sui) on Kaggle, from the DataCamp project of the same name; license listed as "Unknown", so the raw data is not redistributed — the repository ships a download script. Simulations use fixed seeds and are reproducible from the repository.

Built to learn: a portfolio project by Omid Golchin. Nothing here is a claim of a new method — it is classic machinery, implemented carefully, with the failure modes left in plain sight.
